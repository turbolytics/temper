# Temper v0.1 — design

Date: 2026-11-14
Status: approved 2026-11-14

## Intent

Temper codifies an approach already running inside two Turbolytics projects
and releases it as a standalone, open-source tool.

- **sql-flow** has the prototype: `internal/coverage` (Go test markers written
  as `COVERS …` log lines), `scripts/coverage_matrix` (a Python generator that
  reads `go test -json` and pytest reports, derives the level from which
  report a result came from, and joins against `docs/coverage/{features,
  invariants,lattice}.yml` and `docs/coverage/integrations/*.yml`), committed
  per-cell statuses in `docs/coverage/status/`, and a rendered `matrix.md`.
- **sql-flow-control** uses the same idea for behavior over time: scenarios in
  YAML (`internal/gateway/testdata/status-scenarios.yml`) that must cover a
  closed set of heuristics.

The specification is `SPEC.md` at the repo root (v0.1 draft). **The spec is
the source of truth for format and rules; this document covers how the first
release is built and what it contains.** Where this document changes the
spec, it says so and the change is made to `SPEC.md` as part of the work.

Why it matters: a test suite only reports on tests that exist. When an AI
writes code it writes tests that skip, assert nothing, or cover the easy
path, and reports green. Temper turns the question around — what did we say
must be proven, and where is the evidence — so anything declared without
evidence is a visible gap.

## Goals

1. A single Go toolchain: the matrix generator and checker are Go (the user's
   explicit requirement — no Python generator).
2. Ship to the world: `go install github.com/turbolytics/temper/cmd/temper@latest`
   and prebuilt binaries on GitHub releases.
3. A Go adapter in this repo that tests import to emit evidence.
4. A documented, language-neutral **adapter contract** so `temper-python`,
   `temper-nodejs`, `temper-java`, etc. can be built as separate repos that
   produce identical evidence.
5. Temper proves itself with Temper: this repo declares its own features and
   invariants, its tests emit evidence, and its `MATRIX.md` is generated by
   Temper in CI.
6. A runnable example under `examples/` that exercises every concept, so a
   stranger can learn Temper without reading sql-flow.

## Non-goals (for this release)

- Migrating sql-flow or sql-flow-control onto Temper. That follows, and will
  test the format against real use. The design should not make it hard
  (see "Migration-friendliness").
- Adapters for languages other than Go. Python, Node, Java live in their own
  `temper-<lang>` repos, later.
- A scenario runner. Temper validates the scenario envelope and joins the
  evidence a project's own runner emits (spec §11).
- An HTML site or rich pages (sql-flow's `clickhouse-types.mdx`). Markdown and
  JSON only.
- Line coverage, test-quality judgement, or anything listed in spec §16.

## Anti-goals

Any of these would make the release a failure even if it "works":

- A cell reads covered without passing evidence for it (a skip, a failure, a
  name match, a stale file, a test-only double).
- Coverage attributed by test name, file path or anything implicit (R2). The
  prototype's name-based attribution is not carried over.
- Declarations generated from code or tests (R1).
- Unknown ids silently ignored or silently created (R7).
- A tool that needs the reader to know sql-flow to make sense of it.

## Constraints

- Go 1.24 (installed locally); module `github.com/turbolytics/temper`.
- The adapter package (what user tests import) depends only on the standard
  library, so importing it adds nothing to a user's test binary.
- The CLI may use `gopkg.in/yaml.v3` (the prototype already does).
- Generated files are deterministic byte-for-byte for the same inputs, so CI
  can check they are up to date with `git diff --exit-code`.
- Error messages follow spec §14: `file: id message (Rn …)`, one per line,
  actionable by an agent.

## Repository layout

```
SPEC.md                     # the spec (v0.1), committed verbatim from the draft
README.md                   # what, why, quickstart, links
docs/adapters.md            # the adapter contract (normative)
temper.go, …                # package temper: the Go adapter (stdlib only)
cmd/temper/                 # the CLI
internal/…                  # model, load, check, evidence, matrix, render
temper.yml, temper/         # Temper's own declarations (dogfooding)
MATRIX.md                   # Temper's own matrix (generated)
examples/inventory/         # a self-contained example project, own go.mod
```

Internal package boundaries are the builder's call; the prototype's lesson
("each module answers one question") is worth keeping.

## The Go adapter

```go
func TestSinkKafka_FlushRetries(t *testing.T) {
    temper.Covers(t, "sink.flush.keeps_batch", temper.Subject("sink.kafka"))
    // ...
}
```

- `temper.Covers(t testing.TB, ref string, opts ...Option)` records that this
  test proves `ref` (for the given subject, if any). A test may call it
  several times.
- `temper.Subject(id string) Option`.
- `temper.Exempts(t, ref, temper.Subject(id))` — see "Exemption proof" below.
- On the first call in a test, the adapter registers a `t.Cleanup` that,
  when the test ends, writes one evidence record per recorded reference with the
  outcome: `skip` if `t.Skipped()`, `fail` if `t.Failed()`, else `pass`. A
  panicking test must not produce `pass`; mapping a panic to `error` versus
  `fail` is the builder's call, as long as it never reads as a pass.
- Subtests are tests: `t.Name()` (with its `/` path) is the record's `test`.
- The level comes from `TEMPER_LEVEL` and the evidence directory from
  `TEMPER_EVIDENCE`, both set by the runner, never by the test (R4). **If
  either is unset, the adapter does nothing**, so plain `go test` works in a
  project that has not wired Temper in. (No evidence means cells read
  missing, which is loud; nothing is silently credited.)
- Evidence is appended to a file unique to the process
  (e.g. `<level>-<pid>-<random>.jsonl`), because `go test ./...` runs one
  process per package in parallel. Writes within a process are serialized.
- The adapter does not validate references; the CLI does (R7). It does not
  read `temper.yml`.

## The adapter contract — `docs/adapters.md`

The normative description every `temper-<lang>` repo implements:

- Environment: `TEMPER_LEVEL` (required), `TEMPER_EVIDENCE` (required,
  absolute path), `TEMPER_RUN` (optional run id). Unset → record nothing.
- One evidence record per (test, reference) per test execution, written after the
  test's outcome is known, as one JSON object per line (spec §12 fields plus
  the `exempts` form and the optional `scenario` field below).
- Adapters never delete or truncate evidence; clearing is `temper clean`.
- Outcome mapping: only a test that ran to completion with no failure is
  `pass`. Skips, expected-failure markers, retries that eventually passed
  after a failure (record each attempt), setup/teardown errors map to
  `skip`/`fail`/`error` — never `pass`.
- File naming: unique per process; never truncate another process's file.
- A test can never set or override its level.

The Go adapter is the reference implementation and its tests double as the
contract's examples.

## The CLI

```
temper check                    # validate declarations (spec §14); no evidence
temper matrix [--json]          # check + join evidence, write status/ and MATRIX.md
temper matrix --check           # same, but write nothing; fail if committed files differ
temper render                   # rewrite MATRIX.md from status/ only (merge conflicts)
temper run --level <L> -- <cmd> # set TEMPER_LEVEL/TEMPER_EVIDENCE/TEMPER_RUN, run <cmd>,
                                # pass its exit code; appends, never clears
temper clean                    # delete all evidence
temper version
```

- `temper run` is not a test runner; it sets the environment so no project
  wires env vars by hand. It never deletes evidence, so a level may be built
  from several commands (Go tests plus a scenario runner, Go plus pytest),
  each wrapped in its own `temper run --level <L>`.
- Exit codes: `0` all enforced cells covered or exempt; `1` an enforced cell
  is missing or failing; `2` a declaration or evidence error (check failure,
  unknown reference, malformed evidence record); `3` (`--check` only) the committed
  `status/` or `MATRIX.md` differs from what would be written. Errors are
  reported before gaps; when several apply, the highest code wins, so CI
  can always tell "forgot to regenerate" from "a real gap".
- `--json` prints the full result: every cell (item, subject, member, level,
  status, contributing tests with outcomes), every error, and a summary. The
  schema is documented in the README and stable within 0.1.
- The project root is found by walking up from the working directory to the
  nearest `temper.yml`, overridable with `--root`.

### Stale evidence — CI is the authority

Evidence accumulates until `temper clean`. Locally, an old pass can sit in
`.temper/evidence` and a developer may commit statuses built from it. That is
caught, not prevented: CI starts from empty evidence, runs every level, and
`temper matrix --check --all-levels` exits `3` if the committed `status/` or
`MATRIX.md` disagrees with what the fresh evidence produces. The README's
quickstart and the agent guidance tell users to `temper clean` before a full
local run. Evidence records carry no run-scoping; `run` stays informational.

### Levels that did not run

The prototype keeps the committed status for a level that has no report in
this run, so a developer who runs only unit tests locally does not see every
integration cell flip to missing. Temper keeps that behavior:

- A level with **no evidence records** in the evidence directory is *not run*. Its
  cells keep their status from the committed `status/` files (a cell with no
  committed row is written `missing`), and the output names the levels that
  were not run.
- Cells on a not-run level are **not judged**: they never affect the exit
  code. A unit-only local run exits on unit cells alone.
- `--all-levels` (always used in CI) treats every level as run, so its cells
  are judged on the evidence present and a level with none reads missing.

## Checks (`temper check`, and the first step of `temper matrix`)

Everything in spec §14, plus:

- Unknown fields in declaration files are errors (typo protection), except
  inside lattice `answers` entries and scenario `events`, which carry
  project-specific payload.
- Scenario ids may be evidence references (spec §11), so feature, invariant
  and scenario ids share one reference namespace and must not collide.
- A reference to a retired id is an error that names `replaced_by`.
- `applies_to: kind+Capability` resolves against subjects' `implements`.

Evidence-time errors (reported by `temper matrix`, R7):

- An evidence record whose `covers`/`exempts` does not resolve, whose `subject` is not
  declared, that omits `subject` for a per-subject item, or names a subject
  the item does not apply to.
- An evidence record whose `level` is not in `temper.yml`.
- A malformed line (file and line number in the message).
- Evidence naming a `test_only` subject is valid and credits nothing.

## Matrix semantics

Cells and statuses exactly as spec §7–§10 and §13. Points the spec leaves
open, settled here:

- **Lattice member keys** are not ids: a key is any string without
  whitespace or `/` (sql-flow uses `list<int64>`). The reference form is
  `lattice/key`, split on the first `/`.
- **Lattice answers**: `supported` (string), or a map. A map with
  `unsupported: true` needs `reason` and either `proven_by` or `tracked_by`;
  with `tracked_by` and no `proven_by` the cell is unenforced. A map without
  `unsupported` counts as supported. Extra keys are kept and ignored, so
  sql-flow's `outcome/columns/expect` payloads load unchanged.
- **Scenario provenance — a change to the spec.** An evidence record may carry
  `scenario: <id>`, set by the project's scenario runner (adapters expose
  it, e.g. `temper.Scenario(id)` as an option in Go). When present, the
  scenario must be declared and its `covers` must include the record's
  reference (and its `subject`, if the scenario declares one), else it is an
  evidence error (R7). The runner emits one evidence record per `covers` reference
  plus one covering the scenario id itself, all carrying `scenario`.
- **Scenario-covered lattices**: a member is covered at a level only by a
  passing evidence record that covers `lattice/member` **and** carries a `scenario`
  whose declaration lists that member. Plain test evidence does not count.
  `temper check` reports a member that no declared scenario lists in its
  `covers` (R6 gap), before any test runs.
- **Scenario `subject`**: the envelope gains an optional `subject` field, so
  a scenario can cover a per-subject invariant or feature; its evidence
  carries that subject. A scenario covering a per-subject item without a
  `subject` is a check error.
- **Exempt status** applies at each required level where the proof passed;
  where it did not, the cell is missing (or failing, if the proof failed).
- **Invariant `requires: []`** produces no cells; it is listed in the matrix
  as declared, with its `tracked_by` if any.
- **Unenforced cells** (item has `tracked_by` or `enforced: false`): the cell
  reads `covered` when passing evidence exists — so a tracked item that is
  now proven shows as ready to enforce — and `unenforced` otherwise. Neither
  affects the exit code.
- **Unsupported answers** produce cells (spec §9 is amended to say so): with
  `proven_by`, the cell is `exempt` when the proof passes and missing or
  failing otherwise; with only `tracked_by`, the cell is `unenforced`.

### Exemption proof — a change to the spec

R5 says an exemption is proven by a passing test. The spec gives the test's
id in `proven_by`, but Temper only sees evidence, and an evidence record states what a
test *proves*, not that it *exists*. If the proving test emitted
`covers: <invariant>` it would read as covering the invariant — the opposite
claim.

So an evidence record has one of two forms: `covers` (proves the claim) or `exempts`
(proves the subject is legitimately excused from it). The proving test calls
`temper.Exempts(t, "sink.flush.idempotent_on_key", temper.Subject("sink.kafka"))`.
A cell is exempt when the subject declares the exemption **and** a passing
`exempts` evidence record for that (reference, subject) exists at the level **and**
its `test` equals the declared `proven_by`. The same applies to `unsupported`
lattice answers (`exempts: sink.types/list<int64>`). An `exempts` record
with no matching declaration is an error (R7).

### Spec amendments made as part of this work

`SPEC.md` stays v0.1 and is edited to match: `exempts` evidence records (§10, §12);
the `scenario` evidence field and optional scenario `subject` (§11, §12);
cells for unsupported answers (§9); `status/` subdirectories (§4); looser
lattice keys (§5); scenario ids in the reference namespace (§5); `temper
run`/`temper clean` and exit codes (§13).

## Committed outputs

- `status/` holds one status per cell, no test names or counts, one row per
  line in a flow mapping, sorted by id (the prototype's format, chosen so git
  merges two branches that flip different rows):

  ```
  # Generated by temper. Do not edit by hand.
  sink.flush.keeps_batch: {unit: not_required, integration: covered}
  ```

  Layout (a change from spec §4's flat `status/<id>.yml`, because ids are
  unique only within a kind): `status/features.yml`,
  `status/subjects/<subject>.yml` (invariant rows and `lattice/member` rows),
  `status/lattices/<lattice>.yml` (scenario-covered lattices). Files the
  generator no longer owns are removed.
- `MATRIX.md` is rendered **from `status/` plus the declarations only**,
  never from evidence, so it changes only when a status does. It carries a
  header saying it is generated, a legend, a summary of counts by status,
  then sections for features, invariants (grouped by `family` where set),
  subject lattices, and scenario-covered lattices. Unenforced items show their
  `tracked_by`; invariants show `violated_once`. Exact table shapes are the
  builder's call within those constraints; they must read well at
  sql-flow's size (~40 features, ~60 invariants, ~20 subjects).
- `temper matrix --check` fails when either output differs from what would be
  written, so CI catches an uncommitted regeneration.

## Dogfooding

This repo has `temper.yml` with levels `unit` (`go test ./...`) and
`integration` (the built binary run against `examples/inventory` and fixture
projects). It declares features (`cli.check`, `cli.matrix`, `adapter.go`, …)
and invariants that encode the anti-goals — for example "a skip never
covers", "an unknown reference fails the run", "an exemption without a
passing proof is not exempt", "generated output is deterministic". CI runs
the levels through `temper run`, then `temper matrix --check`. The exact
lists are the builder's call; the anti-goals above must each appear as an
invariant.

## The example — `examples/inventory`

A small, self-contained Go module (own `go.mod` with a `replace` to the repo
root) for a made-up inventory service. It must show, with passing tests and
a committed `MATRIX.md`:

- features at more than one level;
- a visible gap: an invariant with `tracked_by` that no test proves yet, so a
  reader sees what a gap looks like while the example still exits `0`;
- two subjects of one kind (e.g. a memory store and a file store) under a
  shared invariant set, with one exemption proven by `temper.Exempts`;
- a subject lattice with one `unsupported` answer;
- a scenario-covered lattice with a tiny project-owned scenario runner that
  emits evidence per `covers` plus the scenario id.

## Migration-friendliness

Not built now, but nothing may block it: sql-flow's declarations should map
onto Temper's by renaming (`integrations/` → `subjects/`, `types:` →
`answers:`, `lattice.yml` → `lattices/<id>.yml`) and replacing
`coverage.Covers`/`coverage.Invariant` with `temper.Covers`. Where sql-flow
relies on name-based attribution, migration means adding explicit evidence —
that is intended.

## Release

- Tag `v0.1.0`; GoReleaser builds darwin/linux/windows × amd64/arm64 binaries
  to GitHub releases via a GitHub Actions workflow on tag push.
- CI on every push: `go vet`, `go test` (through `temper run`), the
  integration level, the example, and `temper matrix --check` for both this
  repo and the example.
- README: the problem in a paragraph, a 5-minute quickstart against the
  example, the CLI, the adapter contract link, and the agent guidance from
  spec §15.

## Left to the builder

Internal package structure; table shapes in `MATRIX.md` within the stated
constraints; the exact `--json` schema (documented, stable within 0.1);
panic → `error` vs `fail`; the exact feature/invariant lists for dogfooding
(anti-goals must be covered); the example's domain details.

## Calls made without explicit sign-off

1. Adapters for other languages live in separate `temper-<lang>` repos; this
   repo ships only the Go adapter.
2. Adapter is a no-op when `TEMPER_LEVEL`/`TEMPER_EVIDENCE` are unset.
3. `temper run` exists to set the environment; it appends and never clears.
   (Stale evidence: CI is the authority, `temper clean` clears — agreed.)
   Scenario provenance via a `scenario` evidence field and optional scenario
   `subject` — agreed.
4. Levels with no evidence keep their committed status unless `--all-levels`.
5. `exempts` evidence records (a spec change) for exemption and unsupported proofs.
6. `status/` uses subdirectories per kind (a spec change).
7. Lattice keys are looser than ids; answer maps may carry extra fields.
8. Scenario ids share the reference namespace with features and invariants.
9. Strict unknown-field checking in declarations outside payload areas.
10. Exit code `3` for stale generated files under `--check`.
11. Not-run levels are never judged locally; CI always passes `--all-levels`.
12. Unenforced cells show `covered` once proven; unsupported answers are cells.
13. The example's visible gap is a `tracked_by` invariant, so it exits `0`.
