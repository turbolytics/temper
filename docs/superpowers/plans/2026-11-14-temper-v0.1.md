# Temper v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Temper v0.1: a Go CLI (`temper check|matrix|render|run|clean|version`) and a stdlib-only Go adapter that tests import, proven by Temper's own matrix and a runnable example.

**Architecture:** The root package `temper` is the adapter: tests call `temper.Covers`/`temper.Exempts`, and a `t.Cleanup` appends JSON-lines evidence records to `$TEMPER_EVIDENCE`. The CLI loads declarations (`internal/load` → `internal/model`), validates them (`internal/check`), reads and validates evidence (`internal/evidence`), joins both into cells (`internal/matrix`), and writes committed status files (`internal/status`) and `MATRIX.md` (`internal/render`). `cmd/temper` wires it together and owns exit codes and JSON output.

**Tech Stack:** Go 1.24, `gopkg.in/yaml.v3` (CLI only), stdlib `flag`, `encoding/json`, `testing`. GoReleaser + GitHub Actions for release.

**Spec:** `docs/superpowers/specs/2026-11-14-temper-design.md` (the design) and `SPEC.md` (format and rules). Read both before any task.

## Global Constraints

- Module path `github.com/turbolytics/temper`; `go 1.24` in `go.mod`.
- The root package `temper` imports the standard library only. Nothing under `internal/` may be imported by it.
- Only `gopkg.in/yaml.v3` may be added as a dependency (CLI side). No CLI framework.
- Error line format (spec §14): `<file>: <id> <message> (<rule>)` — omit `<id> ` when there is none, omit ` (<rule>)` when there is none. `<file>` is relative to the project root, forward slashes.
- Generated files start with a header saying they are generated: status files `# Generated by temper. Do not edit by hand.`; `MATRIX.md` `<!-- Generated by temper. Do not edit by hand. -->`.
- Generated output is byte-for-byte deterministic: every map iterated in sorted order, levels in `temper.yml` order, `\n` line endings, trailing newline.
- Status values (exact strings): `covered`, `exempt`, `failing`, `missing`, `unenforced`, `not_required`.
- Exit codes: `0` ok; `1` an enforced, judged cell is `missing` or `failing`; `2` a declaration or evidence error, or a usage error; `3` (`matrix --check` only) committed output differs. Highest applicable wins.
- Environment: `TEMPER_LEVEL`, `TEMPER_EVIDENCE` (absolute), `TEMPER_RUN`. The adapter records nothing unless both of the first two are set.
- Config defaults: `evidence: .temper/evidence`, `dir: temper`, `matrix: MATRIX.md`. Status files live in `<dir>/status/`.
- Never use "warrant" anywhere; the term is "evidence" / "evidence record".
- Every test that proves a dogfood id calls `temper.Covers` with it (ids in the table below). Tests run without `TEMPER_*` set are unaffected (adapter no-op).

## Review Focus

1. **No evidence directory yet** (fresh clone, first `temper matrix`): every level is not-run, the run writes all-missing rows, exits 0 locally; with `--all-levels` exits 1. Never a crash. → Task 7 test `TestBuild_NoEvidenceAllNotRun`, Task 5 test `TestRead_MissingDir`.
2. **Parallel processes and goroutines writing evidence** (`go test ./...`, `t.Parallel`): every line in every file is one valid JSON object. → Task 1 test `TestRecorder_ConcurrentWritesStayWhole`.
3. **Empty or malformed YAML** (empty `features.yml`, a tab-indented file, a list where a map belongs): empty files load as empty; malformed ones yield an error naming the file, never a panic. → Task 2 tests `TestLoad_EmptyFilesAreEmpty`, `TestLoad_MalformedNamesFile`.
4. **Lattice keys that need YAML quoting** in status files (`list<int64>`, `a:b`, `#x`): they round-trip through `status.Files` → `status.Read` unchanged. → Task 9 test `TestStatus_KeysRoundTrip`.
5. **Evidence files with CRLF line endings or trailing blank lines** (written on Windows, hand-edited): parsed as if `\n`; blank lines skipped. → Task 5 test `TestRead_CRLFAndBlankLines`.

**Files:**

- Test: `internal/matrix/matrix_test.go` (Go-built projects and `[]evidence.Located`; helper `rec(covers, subject, test, level, outcome string) evidence.Located` and `ex(exempts, subject, test, level, outcome string)`)

**Interfaces:**
- Consumes: `model`, `evidence.Located`, `status`.
- Produces:
  - `type matrix.Options struct { AllLevels bool }`
  - `type matrix.Evidence struct { Test, Outcome string }`
  - `type matrix.Cell struct { Kind, Item, Member, Subject, Level string; Status status.Status; Enforced, Judged bool; Evidence []Evidence }`
  - `type matrix.Result struct { Levels, NotRun []string; Cells []Cell; Set status.Set }`
  - `func matrix.Build(p *model.Project, recs []evidence.Located, committed status.Set, opt Options) Result`
  - `func (r Result) Gaps() []Cell` (Enforced && Judged && status ∈ {missing, failing}); `func (r Result) Summary() map[status.Status]int` (over `Cells`)

Semantics (from the design, "Matrix semantics"):
- A level is *run* when any record (after validation) has that level, or `AllLevels`. `NotRun` lists the others in config order.
- Judging a set of records `rs` for one cell at one level: any `pass` → covered; else any `fail`/`error` → failing; else missing (skips count as nothing — R3).
- Feature (not retired): cell per level in `requires`, from `covers == id` records. Row in `Set.Features` for every non-retired feature, all config levels, `not_required` where not required.
- Invariant (not retired, `requires` non-empty): for each `ApplicableSubjects` subject and each required level. If the subject declares an exemption for it: judge `exempts == id && subject == s && test == proven_by` records, mapping covered → `exempt`. Else judge `covers == id && subject == s`. If `!IsEnforced()`: `Enforced=false` and any non-covered, non-exempt status becomes `unenforced`. Row in `Set.Subjects[s][id]`.
- A cell on a not-run level: `Judged=false`, status = committed value when present and not `not_required`, else `missing` (unenforced items: `unenforced`). `Evidence` empty.
- `Cells` sorted by Kind (feature, invariant, lattice), Item, Subject, Member, then level index. `Evidence` sorted by Test then Outcome.
