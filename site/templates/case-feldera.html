Case study · November 2026

Feldera's incremental views under an outside audit

Summary

Feldera keeps SQL views up to date as data changes. It doesn't rerun the whole query each time. Instead, it updates the result with just the change. Feldera's promise is that the result always matches running the full query from scratch.

We tested that promise on the open-source edition, version 0.383.0.

It held up. We found two edge cases. The Feldera team asked us to file both as issues. One already has a fix in review.

What we checked

We changed the data in many ways and checked every view after each change. Each time, we asked one question: does the view match the same query run from scratch?

We tried:

  • Many kinds of change. Inserts, deletes, updates, and emptying a table completely.
  • Different thread counts. 1, 4 and 8 workers.
  • Every SQL type. All 29, including numbers, text, dates, timestamps, UUIDs, arrays, rows and maps.

To get the right answer, we ran each query from scratch in DuckDB. To check the types, we followed Feldera's own docs on how each type compares and sorts. For the empty-table case, we checked what PostgreSQL and DuckDB return.

What held up

  • 65 views matched after every change. They cover joins, GROUP BY, window functions, time windows, subqueries, UNION and EXCEPT, and recursive queries.
  • All 29 types worked correctly in GROUP BY, DISTINCT, joins, MIN and MAX, and ORDER BY. SUM gave the right totals for every numeric type. Its one failure was the DECIMAL overflow below.
  • Worker count didn't change the results. 1, 4 and 8 workers gave the same answers.
  • Other features worked too. These include transactions, primary keys, Kafka through broker outages, and the PostgreSQL output.

In total, 547 of 560 tests passed. All 13 failures came from the two edge cases below.

The two edge cases

1. A DECIMAL SUM could crash the pipeline (#8032)

When the same row arrives twice in one request, Feldera stores it once with a count of 2. To compute the SUM, it multiplies the value by 2. For a very large DECIMAL(38, 10) value, that multiplication went past 38 digits and crashed the pipeline. The real total still fit.

Status: Ben Pfaff, the main author of Feldera's fixed-point decimal library, asked to take it.

2. ROLLUP returned nothing on an empty table (#8033)

On an empty table, PostgreSQL and DuckDB return one grand-total row for ROLLUP, CUBE and GROUPING SETS. Feldera returned no rows. This happened on a new table, and again after a table was emptied.

Status: Mihai Budiu opened a fix the same day (PR #8034).

How the team responded

We first posted the results as a discussion. The maintainers replied that day and asked for the two issues. Each issue had an owner right away.

What we learned

  • A clear promise is easy to test. "Matches the query from scratch" applies to every view.
  • Bugs hide at the edges. Both issues showed up only at extremes: the largest DECIMAL and the empty table.
  • Sharing what worked helps. Leading with what held up made the two issues easy to act on.

Out of scope

Crash recovery and graceful stop require the Enterprise edition, so we didn't test them.
