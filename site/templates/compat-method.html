Compatibility

How the compatibility method works

Method version {{.Version}} · updated {{.Date}}

Many products sell on a claim such as "Postgres-compatible". We test that claim. The harness runs the same SQL statements on PostgreSQL and on your product, and compares every answer.

  • What it checks. {{commas .Total}} PostgreSQL 17 features, using {{commas .Control.Statements}} statements from PostgreSQL's own tests, its documentation and real applications.
  • Why you can trust it. The method is open source. When the harness tests PostgreSQL against itself, it finds no differences. Every finding comes with a one-command reproduction.
  • What you get. A report that leads with crashes and silent wrong answers, followed by a score and how much of your product it covers.
  • What gets published. Open-source results, after at least 7 days of review by the maintainers. A paid or private report, only with the vendor's approval. See Fairness.

Your product is compatible with PostgreSQL when it gives PostgreSQL's answer to the same statement. That means the same rows, the same column types, or the same error code. The method checks this for every statement in its corpus and every feature in its inventory.

Fairness

Turbolytics runs every test. Payment never changes results. A paying vendor gets a private report first, reruns on every release, and branding. We'll never change our answers based on payment.

We test open-source products without being asked. We test hosted commercial services only with the vendor's permission.

Results follow two publication rules:

  • For an open-source product, results are published after its maintainers have had at least 7 days to review them. Their corrections are included.
  • A paid or private report is published only with the vendor's approval.

For each finding, the published report shows the statement, both answers and the command that reproduces it. It also shows the score with its coverage, the method version and every pinned version.

To dispute a finding or your product's scope, reply during the review, or open an issue on the Temper repository. A finding that turns out to be the harness's fault is removed before publication.

The score

Version {{.Version}} scores five lists: SQL commands, query syntax, functions, operators and data types, less what your product doesn't claim. Server settings, error codes, system catalogs and SQL-standard features appear in the report but aren't scored yet.

The score is the share of tested features that pass, weighted by how often the captured applications use each one. A feature is tested when the corpus decided it: it passed, failed, or hit a documented difference. Untested and undecided features are left out of the score. The report shows them as coverage, right beside the score. A feature no application uses still counts, at a small floor weight.

The score always appears with its coverage and the counts of crashes and silent wrong answers.

Every statement ends with one of 11 outcomes, such as a match, a crash or a silent wrong answer. The harness's README lists them all.

A feature that passes in one statement and fails in another counts as a pass. So the score measures how many features work at all, not how often they give the right answer. Read it beside the findings.

From statements to features

A feature passes when a statement that uses it matches PostgreSQL, and PostgreSQL itself answered without an error. When a statement fails, the method looks for the features in it that no matching statement has proven. If only one is unproven, the failure is attributed to that feature, and the statement becomes its reproduction. If several are unproven, each one is marked undecided. The method never guesses between them. If every feature in the statement is already proven, the failure is attributed to none of them. The report still counts that statement.

An attribution can be wrong when a failure comes from how two features interact. That is why each one is shown with its statement and both answers.

Claims

We set your product's scope from its public documentation, not from the vendor's say-so. That way, a product can't raise its score by claiming less. Each part of PostgreSQL a product doesn't claim is recorded in the method, citing the page and the words it comes from. A vendor can dispute the scope during the review.

Separately, the harness detects, statement by statement, when your product hands a statement to PostgreSQL instead of running it. That statement counts as not claimed, never as a match.

How a statement is compared

Each statement runs on three servers: two independent PostgreSQL servers and your product. Every server starts empty, with the session settings PostgreSQL's own test runner uses. The harness compares the answers row by row. It compares column types by name, and errors by SQLSTATE.

The second PostgreSQL server is the control. Some statements have no fixed answer, such as random() or a timing. When the two PostgreSQL servers disagree, the statement is dropped as noise. It proves nothing either way.

Values that only make sense on one server, such as object IDs, are masked before the comparison. Results that depend on the query plan, such as an aggregate without ORDER BY, never count as a difference.

The inventory

The inventory is the list of features the method checks. The harness generates it from PostgreSQL's own source at tag {{.Tag}} and from a running server's catalogs. A function, operator or type enters the inventory only if PostgreSQL both documents it and has it. The same input always generates the same inventory.

The corpus

The corpus is the set of SQL statements the harness runs. It comes from three sources:

  • PostgreSQL's regression tests. They run in the order of PostgreSQL's own test schedule, on one shared database, with a new session for each file.
  • PostgreSQL's documentation. The examples in the docs, including the examples in the function tables.
  • Real applications. A PostgreSQL server logged every statement while each application's tests ran. Each distinct statement shape enters the corpus once.

Checking the harness

Before any result counts, the harness runs against PostgreSQL itself. On PostgreSQL 17.12, {{commas .Control.Matched}} of the {{commas .Control.Statements}} statements matched. The other {{commas .Control.Noise}} ({{.Control.NoiseShare}}) were dropped as noise, because the two PostgreSQL servers disagreed. None differed.

When your product can switch its own engine off, the harness also runs against your product with that engine off. That run must show no differences either. Both checks have caught harness bugs that would otherwise have read as the product's bugs.

Limits

  • SQL-standard feature IDs aren't scored yet, because no statement maps to one.
  • Casts between types aren't separate features yet.
  • The method checks answers. It doesn't measure performance or behavior under concurrent load.
