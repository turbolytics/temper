Tutorial

Design with Temper

Temper checks that your tests prove what your system promises. This tutorial walks through how Temper tests itself. Every snippet below comes from Temper's repository.

How it works

You write down two lists. The first says what the system does. The second says what it must never do. You keep both lists in YAML files, in a temper/ directory. We call these files the declarations.

Each test then says which items on those lists it proves. Temper runs the tests and builds a table called the matrix. The matrix shows what is proven and what isn't.

You work in this order:

  1. Decide what counts as proof.
  2. List what the system does.
  3. List what it must never do.
  4. Make each test say what it proves.

1 Decide what counts as proof

A level is one kind of test run. Temper has two levels. Unit tests check the logic. Integration tests run the built binary against real projects.

Name each level for what it proves, not for the tool that runs it. The description says what a pass at that level means.

2 List what the system does

A feature is one thing the system does. Write it so a person can check it. requires lists the levels that must prove it.

Write features before the code. A list generated from the code shows only what exists. It can't show what's missing.

3 Write what must never happen

An invariant is a rule the system must never break. This step matters most. Ask what would make the system a failure, even if it seems to work.

For Temper, the worst failure is a matrix that says a test proved something when it didn't. So Temper's invariants are about honesty.

A subject is one concrete part of the system that a rule applies to. Temper's subjects include its command-line tool, cli, and its Go library, adapter.go. Each invariant has these fields:

  • claim: the rule, in one or two sentences.
  • applies_to: the kind of subject the rule is about.
  • class: safety means something bad never happens. liveness means something good eventually happens.
  • family: a label that groups related rules.
  • requires: the levels that must prove the rule.

4 List every case

Some rules cover a fixed set of values. A lattice is that set, written out in full.

Here is an example. Each time a test runs, Temper records how it ended. That record is called evidence. A test can end in four ways: pass, fail, skip or error. Temper's lattice lists all four.

temper/lattices/outcomes.yml

{{index .Snippets "lattice"}}

An adapter is the small library a test calls to report what it proves. Temper has one for Go. Each subject file says, under answers, whether the subject supports each value. The Go adapter supports all four.

Nothing is guessed. temper check validates the declarations without running any tests. Suppose a new adapter leaves out error. Then temper check fails.

5 Make each test state what it proves

A test calls temper.Covers once for each item it proves. temper.Subject names the subject, when the item is an invariant.

This test proves the first invariant from step 3. It records two skipped tests. Then it checks that the matrix still shows the item as not proven.

Temper never guesses what a test proves from its name. Only temper.Covers counts.

6 Run it, and read the result

Run each level through temper run. It tells the tests which level they run at, so no test can choose its own. Then build the matrix:

temper clean
temper run --level unit -- go test ./...
temper run --level integration -- go test -tags integration -run '^TestIntegration' ./...
temper matrix --all-levels

The matrix has one row for each feature and invariant. Its columns are levels, or subjects for invariants. Each cell holds one status. Here is what each status means, and what to do about it.

StatusMeaningWhat to do
✅ coveredA test proved it, and no test for it failed.Nothing.
⬜ missingNo test proved it. A skipped test lands here.Write the test. Don't weaken the rule.
❌ failingA test for it failed or errored.Fix the code or the test. Never skip it.
☑️ exemptThe subject is excused from the rule, and a test proves why.Keep that test.
⛔ unsupportedThe subject doesn't support a lattice value, and a test proves it refuses it.Keep that test.
⏳ unenforcedA known gap, tracked in an issue.Close the issue, then remove tracked_by.

7 Hand it to an LLM

People own the declarations. An LLM writes the code and the tests. Give it the declarations and the guide. temper guide prints the guide. In CI, run every level and fail the build when a cell isn't covered.

The LLM can't pass by cutting corners:

  • A skipped test never covers a cell.
  • A test can't choose its own level.
  • A change to a rule shows up in code review, because people own the declarations.
