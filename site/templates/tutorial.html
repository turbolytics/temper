Tutorial

Design with Temper

This tutorial designs a real project: Temper itself. Temper is built with Temper. Every snippet below comes from its repository, and the matrix at the end is its own.

You design in this order. Decide what counts as proof. Say what the system does. Say what it must never do. Then make each test state what it proves.

1 Decide what counts as proof

A level is one kind of proof. Temper has two. Unit tests check that the logic is right. Integration tests run the built binary against real projects. Name each level for what it proves, not for the tool that runs it.

2 List what the system does

A feature is one thing the system does, written so a person can check it. requires lists the levels that must prove it. Write features before the code. A list generated from the code describes only what exists. It cannot show what is missing.

temper/features.yml (two of them)

3 Write what must never happen

An invariant is a promise the system never breaks. This step matters most. Ask what would make the system a failure, even if it technically works. For Temper, the worst failure is a green matrix that hides a gap. So its invariants are about honesty. applies_to names the kind of subject the promise is about.

4 List every case

Some promises cover a complete list of values. A lattice is that list. Every test outcome is one, so Temper declares all four.

temper/lattices/outcomes.yml

{{index .Snippets "lattice"}}

A subject is one concrete thing the promises apply to. Each subject must say, for every value, whether it supports it. The Go adapter supports all four. A new adapter that leaves out error fails temper check. Nothing is guessed.

5 Make each test state what it proves

A test calls temper.Covers once for each claim it proves. This test proves the invariant from step 3. It records two skipped tests and checks that the cell stays missing. Temper never infers a claim from a test's name.

6 Run it, and read the result

Run each level through temper run, then build the matrix:

temper clean
temper run --level unit -- go test ./...
temper run --level integration -- go test -tags integration -run '^TestIntegration' ./...
temper matrix --all-levels

Each cell has one status. Here is what to do about each.

StatusMeaningWhat to do
✅ coveredA passing test claimed it, and no test that claimed it failed.Nothing.
⬜ missingNo passing evidence. Every skip lands here.Write the test that proves the claim. Do not weaken the declaration.
❌ failingA test that claimed it failed or errored.Fix the code or the test. Never skip it.
☑️ exemptThe subject is excused, and a passing test proves it.Keep the proving test.
⏳ unenforcedA known gap, tracked in an issue.Close the issue, then remove tracked_by.

7 Hand it to an LLM

People own the declarations. An LLM writes the code and the tests. Give it the declarations and the guide, which temper guide prints. CI runs every level and fails the build on a gap.

The LLM cannot pass by cutting corners. A skipped test never covers a cell. A test cannot choose its own level. A change to an invariant shows up in review, because people own that file.
