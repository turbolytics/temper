Compatibility

Compatibility matrices

Many products sell on a claim such as "Postgres-compatible". A compatibility matrix tests that claim. It runs the same statements on PostgreSQL and on the product, and compares the answers feature by feature.

This page explains the method. The PostgreSQL 17 feature inventory lists every feature it checks. The method is open source, in compat/postgres in the Temper repository.

What it measures

A system is compatible with PostgreSQL when it gives PostgreSQL's answer to the same statement. That means the same rows, the same column types and names, or the same error code. The matrix checks this for every statement in its corpus and every feature in its inventory.

The inventory

The inventory is the list of features the matrix checks. It is generated from PostgreSQL's own source at tag {{.Tag}} and from a running server's catalogs. A function, operator or type enters the inventory only if PostgreSQL both documents it and has it. The same input always generates the same inventory.

The corpus

The corpus is the set of SQL statements the matrix runs. It comes from three sources:

  • PostgreSQL's regression tests. They run in the order of PostgreSQL's own test schedule, on one shared database, with a new session for each file.
  • PostgreSQL's documentation. The examples in the docs, including the examples in the function tables.
  • Real applications. A PostgreSQL server logged every statement while each application's tests ran. Each distinct statement shape enters the corpus once.

How a statement is compared

Each statement runs on three servers: two independent PostgreSQL servers and the system under test. Every server starts empty, with the session settings PostgreSQL's own test runner uses. The answers are compared row by row. Column types are compared by name, and errors by SQLSTATE.

The second PostgreSQL server is the control. Some statements have no fixed answer, such as random() or a timing. When the two PostgreSQL servers disagree, the statement is dropped as noise. It proves nothing either way.

Values that only make sense on one server, such as object IDs, are masked before the comparison. Results that depend on the query plan, such as an aggregate without ORDER BY, never count as a difference.

Outcomes

Every statement ends with one outcome.

MatchThe same answer as PostgreSQL.No. It proves the features the statement uses.
Different answerBoth answered without an error, and the answers differ. This is a silent wrong answer, the most serious outcome.Yes
Different typeThe same values, with a different column type or name.Yes
RefusedThe system returned an error where PostgreSQL answered.Yes
CrashThe system's server process stopped.Yes
DocumentedA difference the system's own documentation describes.Yes, in its own column
Not claimedThe system doesn't claim the feature. For example, a query engine may hand schema changes and writes to PostgreSQL.No
BlockedAn earlier difference prevents a fair test. Examples are an aborted transaction, or a table only one side has.No

From statements to features

A feature passes when a statement that uses it matches PostgreSQL. A failing statement blames the features in it that no matching statement has proven. If only one feature is unproven, that feature fails, and the statement becomes its reproduction. If several are unproven, each one is marked undecided. The method never guesses which one is at fault.

Reports

A report leads with what is broken: crashes first, then silent wrong answers, then refusals. Each finding comes with the statement, both answers and a one-command reproduction.

The score comes last. It is the share of claimed features that pass, weighted by how often the captured applications use each one. A feature no application uses still counts, at a small floor weight.

We publish a system's results only after its maintainers have seen them.

Checking the harness

Before any result counts, the harness runs against PostgreSQL itself. On PostgreSQL 17.12, every one of the 52,296 statements matched or was dropped as noise. There were no differences.

When a system can switch its own engine off, the harness also runs against the system with that engine off. That run must show no differences either. Both checks have caught harness bugs that would otherwise have read as the system's bugs.

Reproduce it

The run needs Docker. Results go to the folder you name, never into the repository.

git clone https://github.com/turbolytics/temper
cd temper
make compat-postgres RESULTS=../results

Limits

  • SQL-standard feature IDs aren't scored yet, because no statement maps to one.
  • Casts between types aren't separate features yet.
  • The matrix checks answers. It doesn't measure performance or behavior under concurrent load.
